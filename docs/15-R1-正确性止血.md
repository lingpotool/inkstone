## R1.1 软件光栅宽高传反（崩溃级）

**症状与证据**：`gfx/raster/software.py` 的 `_row_range(rect, clip, h)` 第三个参数是画布**高度**，
但 `_fill`（约 :150）与 `_stroke`（约 :186）都传了宽度 `w`（`_fill` 根本没接收 `h`）。

实测（审查时验证）：

- 200×100 画布上画 `Rect(0,0,200,150)`（内容溢出底部——滚动列表每帧都在发生）→ **抛 ValueError**；
- 100×200 竖向画布全屏填充 → **底部 100 行静默留空**。

此前没炸是因为测试全用方形画布，且黄金图整幅背景恰好 `bottom == height`。

**修法**：给 `_fill`/`_stroke` 传入画布高度并改调用点。顺手核对 `_column_range` 方向是否对称正确。

**测试**：

- `tests/unit/test_gfx_raster.py` 新增：非方形画布（200×100 与 100×200 两个方向）整幅填充，
  断言四角与边缘像素全部着色、不抛异常；
- 新增：形状溢出画布底部/右部（如 `Rect(0,0,200,150)` 画进 200×100），断言不抛异常且
  可见区域着色正确。

**验收**：新测试在修复前必红（先写测试跑一次确认红），修复后 `pytest tests/unit/test_gfx_raster.py -q` 绿。

## R1.2 形状裁剪的 1px 越界（AGENT.md 已知待办）

**症状**：`_column_range`/`_row_range` 用 `int(right)+1` 当上界，裁剪边恰好落在整数像素时多放一列/一行。
文本路径已用 `ceil` 修正，形状路径未改（AGENT.md「已知待办」第 4 条）。

**修法**：统一为 `ceil` 语义（参照 `software.py` 文本路径 `_clip_columns` 附近的既有推理），
与 R1.1 同批完成。**会波及既有黄金图**——属预期，走 docs/16 §1 的新比对方式更新基线
（若 R2 尚未落地，先按现有方式更新基线并肉眼确认 diff 只在形状右/下边缘 1px）。

**测试**：裁剪边界恰为整数像素的用例（如 clip=(0,0,10,10) 画 Rect(0,0,20,20)），
逐像素断言第 10 列/行之外无墨迹。

## R1.3 layout → paint 脏标记联动（渲染管线断裂）

**根因**：`layout/box.py` 的 `mark_needs_layout` 只冒泡 layout 脏、不置 paint 脏；
`paint_tree`（box.py:248-275）按 paint 脏剪枝。全代码库 `mark_needs_paint` 只有 widget 手写调用。
后果：**任何纯几何变化都不会触发重绘**——`RenderScroll.scroll_to` 只标 layout（scroll.py:111-124），
滚动后 paint 阶段整棵树干净，画面不动；窗口 resize 同理。

**修法（最小侵入）**：在 `RenderBox.layout()` 里，当本次**实际执行了布局**（缓存未命中）
且产出尺寸/偏移与上次不同（或上次没有记录）时，调用 `mark_needs_paint()`。
注意两点：

1. 子级 offset 由父级布局决定——父级 relayout 导致子级位置变化时，子级也要重绘。
   最小正确策略：**凡实际执行过 `perform_layout` 的节点，其自身与所有后代都标 paint**
   （"先正确后缓存"；后续优化再收窄）。
2. 不要用"尺寸变没变"做唯一判据——offset 变、尺寸不变的情况（滚动）恰恰是主场景。

**测试**：

- 滚动：`ScrollView` 装长内容，`scroll_to(50)` 后跑 `paint_tree`，断言产出的显示列表
  与滚动前不同（此前是相同的空增量）；
- resize：同一棵树用不同约束布局两次，断言第二次 paint 产生新指令；
- 不回归：干净树重复 paint 仍被剪枝（现有脏标记测试不红）。

## R1.4 RenderScroll 必须裁剪视口

**根因**：`paint_tree` 只 translate 不 clip；`RenderScroll.paint` 是空钩子。
滚出视口的内容会直接画在视口外。

**修法**：

1. `layout/box.py` 的 `RenderBox` 增加钩子 `paint_clip() -> Rect | None`（默认 `None`）；
2. `paint_tree` 遇到返回非 None 的节点：先向录制器施加裁剪（录制器已有 clip 机制，
   见 `gfx/paint.py`），进入子树，出来后恢复；
3. `layout/scroll.py` 的 `RenderScroll` 覆写 `paint_clip()` 返回视口矩形（本节点 bounds）。

**测试**：ScrollView 滚动后渲染显示列表，断言视口外内容的绘制指令携带了裁剪，
且软件光栅出图后视口外无墨迹。

## R1.5 Flex 基线对齐的交叉轴尺寸 bug

**症状（审查实测）**：Row 中 A(高 50/基线 40) + B(高 20/基线 5)，基线对齐时容器报高 50，
但 B 的底边实际在 y=55——**溢出 5px 且不报 overflow**。参考线取组内最大基线是对的
（AGENT.md 有约定），但容器交叉轴尺寸只取了 `max(子级高度)`（`layout/flex.py:295-302`）。

**修法（Flutter 同款）**：基线对齐参与时，交叉轴尺寸 =
`max(above) + max(below)`，其中 above = 子级 baseline，below = 子级 height − baseline。
无基线对齐子级时维持现状。

**测试**：上面的 A/B 用例参数化，断言容器高 = 55；断言无基线路径行为不变（现有 flex 测试不红）。

## R1.6 `RenderObjectElement.update` 必须标 layout 脏

**症状（审查实测）**：`core/element.py:336-342` 在 `update_render_object` 后只调
`mark_needs_paint()`。宽度属性改 10→200，两帧后 `ro.size.width` 仍是 10。
现有测试 `tests/unit/test_core_trees.py:203-216` 只断言了 `root.width` **字段**，
不断言 `root.size`，把 bug 完美遮蔽。

**修法**：`update_render_object` 之后无条件 `mark_needs_layout()`
（`layout()` 有约束缓存兜底，无几何变化时开销极小）。
**不**采纳"属性 setter 自带脏标记"的大改——那牵动整个 layout 层 API，记入 docs/20 后补。

**测试**：把 `test_core_trees.py:203-216` 的断言从字段改为 `size`（改后该测试在修复前必红）；
另补一条 flex 容器内子级尺寸属性更新的端到端用例。

## R1.7 `_sync_children` 复用路径丢 slot

**症状（审查实测）**：`core/element.py:469-478` 复用子级时调 `reusable.update(widget)`
**不传 slot**（对比 `update_child` 在 :196-197 是传的），且顺序不变时不触发
`_reorder_render_objects`——RenderFlex 里的旧权重永远留档。
`Row([Flexible(Box, flex=1), Flexible(Box, flex=2)])` 改成 flex=[3,1]，两帧后宽度仍 33/67。

**修法**：复用时把 `slot_for(index)` 传入 `update()`；slot 实际变化时，
通知父容器刷新该子级的挂载参数（最小做法：slot 变化即触发一次 `_reorder_render_objects`
或等价的重挂）。注意保持 AGENT.md「slot 必须穿过组件层」的既有约定不回归。

**测试**：上述 flex=[1,2]→[3,1] 用例，断言两帧后宽度为 75/25 且 Element 的 slot 已更新。

## R1.8 build 错误边界

**根因**：`core/element.py:165-169` 先清 `_dirty` 再 `perform_rebuild`；
`core/binding.py:164-169` 先清空整批再逐个 rebuild。任一 `build()` 抛异常 →
该节点 dirty 已清、队列已清、后续节点全部跳过——树停在"widget 已换、子树没更新"的
不一致态，下一帧不重试，无任何错误可见。

**修法**：`flush_build` 内 per-element try/except：

- 单节点异常 → 记录到 `BuildOwner` 上的错误列表（如 `owner.errors: list[...]`，
  含节点路径——`describe_path` 现成），**继续**处理其余节点；
- 失败节点保持 dirty（下一帧重试）；为防死循环，连续失败超过 3 次的节点本帧内不再重试
  并保留错误记录；
- flush 结束后若错误列表非空，**抛出聚合异常**还是静默记录，取前者（响亮失败是铁律 5），
  但要保证树中其余节点已完成本帧。

**测试**：一个子树 build 抛异常 → 兄弟子树正常重建、错误被记录、下一帧重试逻辑正确。

## R1.9 帧调度出口 `on_frame_scheduled`

**根因**：docs/06 §4 承诺"时钟由后端注入、vsync 对齐"，但 `BuildOwner` 没有任何
"需要一帧"的出口——`schedule_build_for` 只入队，`begin_frame` 只能外部手动调，
`app.py` 是 8 行空壳。**set_state → 屏幕刷新的闭环目前不存在**。

**修法**：

```python
class BuildOwner:
    on_frame_scheduled: Callable[[], None] | None = None
```

- `mark_needs_build` / `mark_needs_paint` 导致脏集合从空变非空时，调用一次
  `on_frame_scheduled()`（注册一次、帧末注销的语义：在 `begin_frame` 末尾重置
  "已通知"标志，避免每帧重复回调）；
- 这是 app 层、后端 vsync、`motion/` 包共同的接入点，签名保持最简单形态。

**测试**：set_state → 回调恰好触发一次；连续 100 次 set_state → 仍只触发一次；
`begin_frame` 后再标脏 → 再次触发。

## R1.10 主题热切换（最小版）

**根因**：`BuildOwner.theme` 是普通可变属性（binding.py:87），`Element.theme` 活读它，
但样式只在 mount/update 的 `_apply_style` 时应用——运行时换主题，整棵树静默保留旧色。

**修法（最小版，正式机制在 docs/20）**：

1. `theme` 改为 property，setter 里完成：`self._theme = value` + 全树 `mark_needs_build`；
2. 保留直接读取路径不变（`Element.theme` 的活读语义不变）。

**测试**：构建亮色树 → 记下某 Button 背景 → `owner.theme = Theme.dark()` →
跑一帧 → 断言背景变为暗色令牌值；断言重建确实发生（build 计数器）。
