# 22 · GL 后端子包（R7.5 数据驱动的决策与范围）

> 本文不是"想做个 GL 后端"，而是 **R7.5 预先写死的决策规则被数据触发**之后
> 立的分包文档。规则与数字都先于实现固定在这里，避免"量完再调阈值"。

## 1. 决策规则（R7.5 施工前写死）

- 工具：`benchmarks/run.py`（stdlib，无新依赖）。
- 场景：长列表滚动、全屏重绘、文本密集页，各测 p50/p95（**不看平均值**）。
- 规则：任一场景 **p95 > 10ms**（60fps 预算 16.6ms 的六成）→ 启动 GL 后端子包；
  否则记入 `docs/20 §R6.4` 后补清单，GL 让位于 Phase 2 铺组件。

## 2. 实测（2026-09-13，Windows 本机，软件光栅，帧=60）

| 场景 | p50 | p95 | max | mean |
|---|---|---|---|---|
| scroll（150 卡滚动，仅脏子树） | 774.6ms | 859.5ms | 1104.5ms | 777.1ms |
| fullscreen（1280×800 混合树，全量重绘） | 1057.2ms | 3125.0ms | 4410.5ms | 1404.5ms |
| text（40 段中文，整树重排 + 重绘） | 429.8ms | 576.3ms | 627.6ms | 455.5ms |

**p95 超预算 40–300 倍。** 热点用 `cProfile` 定位过，不是测量装置的问题：
`gfx/raster/software.py` 的 `_accumulate` / `_stroke` / `_fill` 是**纯 Python
逐像素 SDF**，一帧要算上百万像素；再加上 `execute` 每次对**整份显示列表**
全量光栅（脏矩形只在合成阶段生效），滚动场景把 150 张卡全部重算。

结论：**软件光栅是"确定性事实源"，不是"生产帧率后端"**（这一点 docs/03 早有
预告）。GL 后端子包由此启动。

## 3. 范围（本包只做这些）

1. **只实现现有显示列表 IR 的指令集**：`FillRectOp`（含圆角）、`StrokeRectOp`、
   `TextRunOp`（字形图集 + 四边形）、`PathFillOp` / `PathStrokeOp`、矩形裁剪。
   **不发明新原语**——IR 是契约（ADR-0008）。
2. **协议不动 core**：沿用 R3.1 的帧生命周期
   `begin_frame(size, scale) → execute(display_list, clip) → end_frame() → screenshot()`；
   `RasterBackend` 增一个实现，`core`/`layout`/`widgets` 一行不改。
3. **不引第二套文本栈**：字形位图仍来自 `HbFtFontEngine`（FreeType 灰度掩码），
   GL 只负责把它们组成图集/纹理。度量与字形同源（ADR-0006 / ADR-0016）不破。
4. **黄金图仍以软件光栅为准**：GL 输出与软件光栅比对时容忍抗锯齿差异
   （docs/03 §3）。CI 不跑 GL（无 GPU），GL 的验收在带 GPU 的 runner 上手动/标记运行。
5. **不做 Skia**：Skia 后端属 Phase 3；自研 GL 先解决"帧率"。

## 4. 验收（DoD）

- 上面三个场景的原样复跑，**p95 ≤ 10ms**（同一台参考机；数字进本文件）。
- 与软件光栅的黄金图比对：几何误差 ≤1px、颜色差异仅限边缘 AA。
- 不改 `core/` / `layout/` / `widgets/`；`test_architecture.py` 全绿。
- 帧缓冲所有权、脏矩形语义与 R3.1 一致；`screenshot()` 仍是显式读回。

## 5. 风险

- SDL2 的 GL 上下文生命周期（无头 CI 无 GL，需 xvfb/离屏或跳过策略）。
- 字形图集管理（动态增长、LRU）；文本是最难的一块，建议先矩形/描边跑通再接文本。
- GL 的浮点/AA 与软件 SDF 不完全一致 → 黄金图**不**切换事实源，避免"换了后端
  界面就变了"的假回归。
